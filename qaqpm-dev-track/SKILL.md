# QAQPM-开发执行（S10）

QAQPM 提供产品目标、PRD 和评测标准；开发流程仓库提供执行规则、技术手册、阶段工具和自检。调用本 Skill 不等于下载、阶段验收或发布已获同意。

## 1. 入口与必读资料

**用**：已决定开发，希望按完整流程从 PRD 做成可验证产品；继续已接入项目；开发中的范围、联调与效果回归。
**不用**：只讨论整合方案或维护 Skill；未确定产品方向（回 S1/S6）；正式验收结论（S11）；部署与上线观察（S12）。普通单点修复不强行启用整套流程。

进入开发前读取 [_shared/development-kit-protocol.md](_shared/development-kit-protocol.md)。它规定首次确认、指定来源、版本固定、资料继承、阶段映射、证据补查和交接，不可用本页摘要代替。

仓库地址：`https://github.com/PerpperQAQ/QAQPMskill-idea-to-launch-kit.git`。

读 S8 PRD/开发与接口约定、S7 标准和题集、S9 选型；外部 PRD 可直接接入，只补必要信息，不要求重写 S1–S9。启用飞书时另读 `_shared/feishu-doc-protocol.md`。

## 2. 首次启动与续做

1. 确认当前产品、PM 文档根、代码位置、本轮范围与交付目标；优先从现有文件和授权中读取。已有工程先只读检查技术栈、目录及工作区改动，判断与仓库既定路径/命令是否兼容；发现不兼容先交适配差异，不先下载后默认接管。为进一步核查确需拉取时仍按第3步确认，并标“待适配”。
2. 有 `dev/开发接入.md`：核实路径、origin、流程基线和工作区变化，读取真实阶段状态，直接续做；不重复下载、不自动更新仓库。
3. 无可用接入记录：告知实际目标路径及仓库用途，询问是否拉取；同项目同位置已授权则执行。未答或拒绝不下载，可以继续计划工作。拉取成功核实来源、提交与必要文件，再创建接入记录。
4. 新产品使用仓库 `projects/<产品名>/`；已有工程先做适配检查，不覆盖旧目录/规则，不搬代码或修改脚本以假装兼容。未适配标明限制。
5. 将 QAQPM 原资料索引及必要快照放入产品 `docs/PRD/`，保留原文为权威；读仓库 `AGENTS.md` 和阶段手册，完成原有阶段0/1核查，不重新询问已定事实，也不跳过所需产物。

## 3. 按图推进开发

默认顺序：

**产品 PRD → 固定项目技术基线 → 分阶段技术开发文档 → 后端可验证 → Agent 初步验证 → 前端可交互 → 前后端联调 → S11 功能测试与 Agent 效果测试。**

- 固定选型指项目采用的模型、技术栈和版本；继承 S9，不为套手册而替换已有架构。
- 先定整体子阶段路线，每个子阶段动手前写当前技术文档：需求引用、范围/不做、接口/数据/状态、实现任务、验证方法与通过线。
- 后端先能独立运行并验证；Agent 核心链路用真实输入、真实模型和可查看结果验证，引用 S7 标准。无 Key 时真实项待验，不能用 mock 通过。
- 默认验证核心能力后再铺正式前端。交互决定效果时，先在技术适配声明中确定最小纵向切片。
- 首个主要终端默认 Web，WAP 可作为移动浏览器适配；桌面客户端、App、小程序按需另定方案，不自动全做，不假设原仓库支持。
- 联调必须走真实 API、登录会话、错误和恢复链路；mock 页面可作开发中间态，不能作为完成证据。
- 登录/数据归属和埋点口径提前设计；部署及上线采集验证交 S12。

## 4. 阶段执行循环

在已绑定仓库根运行 `bash kit.sh 任务 <产品名>`，据其任务和手册实施当前阶段；产物齐备后运行 `bash kit.sh 自检 <产品名>`。

自检通过还要完成共享协议第6节补查。每阶段交付证据和用户可复现步骤；用户明确验收后才执行 `bash kit.sh 通过 <产品名> [下一阶段]`。不能手改流程状态、用 `回到` 绕过失败或把“继续”当所有阶段验收。

续做优先解决上次失败项。通过前确认相关代码/配置和证据仍匹配；改变后重验。仓库当前任务、流程状态、历史由脚本维护；`10`只引用和摘要。

阶段3相关实现和联调完成后交 S11，不能直接开始阶段4部署。用户只要求本地版本时，验收及适用收尾后结束，不劝说或自动推进上线。

## 5. 交付与资料复用

- PM 根：更新 `10-开发推进记录.md`、`dev/开发接入.md`；不重复生成产品 PRD、黄金集或另一份流程状态。
- 产品根：保留仓库要求的阶段技术文档和 `docs/evidence/<阶段>/` 证据包，含原始自检输出、截图、复现清单与真实冒烟记录。
- `eval/runs/`：记录本轮题集、标准、模型/Prompt/代码版本、结果及 bad case；已有跑次引用即可。
- 改实现 → 本站；改范围 → S5/S8；改指标 → S7；选型无法满足 → S9。不得降低标准以通过。
- 功能检查与 AI 效果分开；“有记录”不等于成功，“冒烟成功”不等于正式评测通过。

## 6. Bad case 与飞书

本地-only：沿用已有 Bad case 索引，无则 `dev/bad-cases.md`。飞书模式：沿用/建立 Bad case 多维表（未关闭、本迭代新增、已回写评测集视图）及全字段本地镜像，不另起分散表。回写评测题时同步 S7。

工程证据留原位置；飞书记录摘要、版本及证据链接。分别报告工程验证和文档同步状态，回读不完整不得标飞书交付完成。

## 7. 模板与自检

- [templates/10-开发推进记录.md](templates/10-开发推进记录.md)
- [templates/开发接入.md](templates/开发接入.md)
- [references/prompt-iteration.md](references/prompt-iteration.md)：提示词调优时读取。

自检：
- [ ] 拉取已有明确授权，来源是指定 fork，路径/提交/目标已记录；续做未重复下载或自动更新
- [ ] PRD/标准/选型引用可读，未重开已定决策，已有工程兼容性如实说明
- [ ] 当前阶段按脚本执行，所需文件与证据齐，失败/待验未冒充通过
- [ ] 真实冒烟、前端实际检查、证据新旧已补查；阶段验收有依据
- [ ] Web/移动与其他终端范围明确；前后端真实联调有结果
- [ ] `10`含范围、变更、回归、Bad case、阻塞和接手后第一步；未提前部署
- [ ] 飞书模式已回读对账；未完成同步与工程状态分开

## 8. 交接

给 S11 的第一步：核对候选版本及接入记录，按 S7/S8 读取功能证据和 AI 评测，补齐正式验收缺口。

字段沿用 `_shared/handoff-schema.md`，加 `development_binding_path`、`kit_repo_url`、`kit_baseline_commit`、`kit_root`、`kit_product_root`、`kit_stage`、`delivery_target`、`primary_client`、`evidence_refs`；保留 `scope_drift`、`regression_eval_runs`、Bad case 与飞书字段。下一站 S11，不直接触发 S12。

## 专题文档与协作视图

读取S8引用的同一Agent/RAG/AIGC需求及S7评测对象，沿用实际能力ID与文件，不再写一套平行需求。迭代跑测使用S7的测试Case结构，结果与配置、产物、Bad case相连。

按需使用[开发排期与交接](templates/开发排期与交接.md)映射已有工程任务源；需要个人Todo、日报／周报／月报时用[工作记录与周期复盘](templates/工作记录与周期复盘.md)，从实际证据汇总，不作为阶段硬门槛。来源见[_shared/document-template-sources.md](_shared/document-template-sources.md)。
