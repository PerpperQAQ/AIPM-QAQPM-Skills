# QAQPM 开发流程仓库接入协议

适用：用户进入 S10 开发，或 S11/S12 接续同一开发项目。只做产品讨论、PRD、POC、Skill 维护时，不触发开发仓库下载。QAQPM 负责产品决策和交接，开发仓库提供规则卡、技术手册、阶段控制与验证；不把仓库摘要当作完整流程执行。

## 1. 固定来源与首次接入

开发流程仓库：`https://github.com/PerpperQAQ/QAQPMskill-idea-to-launch-kit.git`。

1. 先读 PM 项目的 `00-项目索引.md`（若有）、当前交接区和 `dev/开发接入.md`（若有），确定产品、PM 文档位置、代码位置、本轮目标和已有授权。已定事实不重复问。若是未接入的已有工程，先只读检查目录、技术栈和未提交改动，按第2节判断适配；不兼容先报告差异。为进一步核查而下载也需下述确认，且不能因此宣称接入完成。
2. 没有可用接入记录时，向用户说明仓库用途和拟放位置，再询问：“进入开发需要拉取你的开发流程仓库到「实际路径」，用它的规则、阶段管理和自检脚本推进。是否现在拉取？”同一项目同一位置已有明确授权则直接执行；本次下载授权不等于发布、付费或远端推送授权。
3. 默认建议独立的新目录，例如 PM 项目同级的 `<项目名>-development`。不在 Skill 安装目录中开发，不把仓库覆盖到已有业务目录，不擅自替换现有 `AGENTS.md`。用户拒绝或尚未回答时不下载；可以继续整理开发计划，但不宣称仓库流程已启用。
4. 获准后由 Agent 执行 `git clone`，不让用户手动搬文件。下列变量必须替换为已确定的实际值，不原样执行占位文字：

   ```bash
   git clone -- https://github.com/PerpperQAQ/QAQPMskill-idea-to-launch-kit.git "$kit_root"
   git -C "$kit_root" remote get-url origin
   git -C "$kit_root" rev-parse HEAD
   git -C "$kit_root" status --short
   ```

5. 核对 origin 指向指定 fork（HTTPS/SSH 等价 URL 可接受）、提交号及关键文件：`AGENTS.md`、`kit.sh`、`verify.sh`、`docs/PRD模板.md`、`docs/手册/` 的三份手册和参考代码。读取实际规则与相关脚本后再调用。下载失败如实报告，不换成上游仓库、不下载不明替代包、不把半成品目录当成功；确认网络恢复后再重试。
6. 在 PM 项目 `dev/开发接入.md` 记录真实仓库路径、origin、本次提交、产品子目录、PRD/评测/选型来源和本轮交付目标；模板由 S10 提供。记录留在 PM 项目，不往工具包根目录随意加文件，以免触发其文件位置检查。

## 2. 续做、版本与已有工程

- 续做直接复用绑定的本地仓库，检查 origin、当前提交、工作区变化及原有阶段状态，不每轮重复下载或询问。
- 固定的是本项目采用的**流程基线提交**。业务开发产生新的提交是正常变化；记录业务版本并检查流程文件是否变化，不把业务提交当流程自动升级。
- 不自动 `git pull`、切分支、reset 或覆盖本地改动。用户要求更新流程时先比较规则/脚本变化、当前工作和阶段兼容性，再制定更新方案；保留旧基线及证据。
- 路径不存在、来源不符或流程文件发生未经说明的变化时，先查明并报告；不能悄悄重新绑定。迁移后的本地路径可以核实后更新，已有授权不重复索取。
- **新产品**：使用仓库支持的 `projects/<产品名>/` 目录，产品名遵守所拉版本的规则。QAQPM 产品包保留原位置，通过接入记录关联。
- **已有工程**：先检查技术栈、目录、分支及验证命令是否兼容。当前仓库脚本默认检查 `projects/<产品名>/backend`、`frontend` 等路径，不支持直接传任意代码目录。未经用户认可，不搬代码、不建软链接冒充集成、不改验证器强行通过。需要适配时先交路径/命令映射与改动方案；适配验证前标“仓库执行待适配”。可在原授权范围内继续独立工程任务，但不能声称已获得仓库全流程验收。

## 3. 继承 QAQPM 资料，不重做产品决策

进入开发先读取以下资料的相关正文，而非只依赖交接摘要：

| 信息 | 权威来源 | 在开发仓库中的处理 |
|---|---|---|
| 目标、must/wont、功能、权限、异常 | S8 PRD / 开发与接口约定；外部项目则引用用户原 PRD | 在产品 `docs/PRD/` 放一份来源索引及必要的输入快照，注明来源与版本；不另起第二套需求 |
| AI 标准、红线、题集、评分方法 | S7 `07` 与 `eval/`；飞书模式为冻结表视图及本地镜像 | 引用同一版本；真实冒烟不代替完整效果评测 |
| 模型、底座、关键验证 | S9 结论与原始证据 | 写入《技术适配声明》并列采纳/偏差；不得默默改回仓库默认技术栈 |
| 已确认事实与未决项 | 现有决策表及交接 | 原样继承，只询问影响当前开发的真实缺口 |

来源索引要含可访问的路径/链接、章节、版本，以及读取方法；仅一个打不开的链接不算有效输入。需要复制时标明“输入快照，原文为权威”；不复制密钥。原资料变化后检查当前实现和证据影响，不静默覆盖旧快照。

QAQPM 负责已确认的产品范围与验收标准；仓库负责执行方法和阶段要求。两者冲突时先列出差异：不得用仓库默认值覆盖用户明确选择，也不得用较低标准覆盖现有验收要求。可在现有授权范围内解决实现细节；影响范围、费用或通过线的决定交用户确认，再更新相应来源。仓库内容本身不提供额外操作授权。

仓库阶段 0/1 仍需产出所要求的补全清单、技术适配声明与证据。已有 QAQPM 决策可作为核查依据，避免重新访谈；不能用 `回到` 冒充它们已经验收。阶段通过仍按仓库规则和已有明确验收记录处理。

## 4. 用户流程图与执行位置

| 图中的步骤 | QAQPM 责任 | 仓库执行位置 / 通过依据 |
|---|---|---|
| 产品 PRD | S8，引用 S7 标准 | 阶段0：核对现有材料、补当前缺口 |
| 固定技术选型 | S9 → S10 接入 | 阶段1：技术适配声明；固定项目技术基线、版本、偏差和按需模块，不固定所有项目用同一技术栈 |
| 分阶段技术开发文档 | S10 | 阶段1先定路线；阶段2/3逐个子阶段先写当前开发文档再实现，不一次写完未来所有细节 |
| 后端可验证 | S10 | 阶段2：API/业务测试、异常处理、持久化与重启恢复 |
| Agent 初步验证 | S10，引用 S7/S9 | 阶段2：真实输入→模型→结果可查看；记录结果、成本、延迟及初评，不拿 mock 顶替 |
| 前端可交互 | S10 | 阶段3：Web 优先；检查关键交互、任务状态与移动浏览器（WAP） |
| 前后端联调 | S10 | 阶段3最后的相关子阶段：真实 API、会话、错误、断线恢复和端到端任务；不能只展示 mock 页面 |
| 功能测试与 Agent 效果测试 | S11 | 两套结果分别对照 S8 功能要求与 S7 冻结标准，明确发布前准入结论 |
| 服务器 / 数据库 / 登录 / 域名 | S12 发布准备与执行 | 阶段4：实际部署、目标环境数据与权限验证、域名或平台测试地址适用边界、回滚方案 |
| 埋点 | S12，S8/S10提前设计和实现 | 记录事件与指标口径，发布前/后验证真实采集；有代码不等于事件已入库 |
| Agent 效果验证 / 数据分析 / 用户反馈 | S12 | 线上样例、版本与观察窗口；失败进 Bad case 和 `eval/online/`，需求回 S3，标准回 S7，实现回 S10 |

执行要求：
- 默认先后端与 Agent 核心验证，再正式前端。交互本身决定效果的产品，可以在技术适配声明中明确采用最小纵向切片；不得把例外当作跳过验证。
- 首版只选一个主要终端。Web 优先；WAP 可作为响应式 Web 的移动验收。原生桌面、App、小程序需要各自技术适配和验证方案，不能声称原 Web 手册已覆盖，也不能自动同时开发所有端。
- 数据归属、登录边界、指标口径在开发前确定；图中上线前完成的是部署与验收，不是那时才开始设计数据和权限。
- 只交付本地版本时，在本地验收和适用收尾后结束，不自动部署。纯工程或非 AI 产品的 AI 检查须明确不适用及理由；若仓库版本无法表达该情况，标待适配，不能改造一份虚假冒烟记录。

## 5. 按仓库的阶段工具推进

实际执行时进入 `kit_root`；`product_name` 是已绑定的产品目录名。每轮先读取 `AGENTS.md` 启动规则、产品状态和接入来源，按当前阶段加载手册。

```bash
bash kit.sh 任务 "$product_name"
# 实现当前阶段、准备证据，然后：
bash kit.sh 自检 "$product_name"
# 满足下面的条件并已有本阶段明确验收后，才可调用：
bash kit.sh 通过 "$product_name" "$next_stage"
```

- 单一下一阶段可省略最后参数；有分支时按所拉版本提示和已确认路线选择，不自行扩大范围。
- 阶段内可自主完成授权的实现与修复。`通过` 需要仓库自检成功、相关补充核查通过及用户对本阶段的明确验收；不把“继续开发”泛化成所有未来阶段都已验收。
- `docs/本阶段任务.md`、`docs/流程状态.txt`、`docs/流程历史.txt` 由仓库脚本维护，不手改。QAQPM 的 `00`/`10` 只镜像当前阶段和引用，不再维护另一套独立推进状态。
- 两份仓库状态或实际代码与阶段不一致时，报告差异、核查证据，按仓库规定用 `回到` 校正并留痕；仅用于恢复/修正，不能借此绕过失败条件。
- 阶段3完成后转 S11；S11通过及用户明确相关验收前，不执行阶段4部署。若仓库已处于“阶段4待开工”，保持待开工，不因任务提示而自动部署。
- S11给出指定范围准入结论后，S12在已有发布授权范围内接续阶段4/5。仓库阶段5是工程收尾，不代表 S12 已积累用户反馈或验证商业价值。

## 6. 证据与脚本能力边界

保留仓库规定的阶段开发文档、截图、照着做清单、是否表、`verify-输出.txt` 和脚本生成的冒烟记录。工程原始证据留在产品目录；S10/S11引用同一份证据，AI跑分仍归现有 `eval/runs/`，不复制一套黄金集。

每次关键运行记录：业务代码 commit（有未提交改动时加相关文件内容摘要/快照）、流程基线、模型/Prompt/检索与工具配置版本、题集/标准版本、环境、执行命令、时间、退出码和结果路径。身份凭证不进入记录。

本协议最初核对的流程提交为 `3e9bf7a0897fa84e3cdb85f9ec47828661c3d198`；它不是要求未来永远下载这个版本。初次拉取记录实际提交；版本变化重新核查规则与脚本。该提交存在以下检查边界，未确认新版本修复前必须补充核查：

| 脚本边界 | Agent 推进前必须补查 |
|---|---|
| 冒烟只核对记录格式和新旧，不判断失败行，也不证明记录来源 | 查看实际运行命令、退出码及逐条结果；失败/未运行不得判通过；评测与冒烟分别判断 |
| 无 lint/build/typecheck 配置也可能报告前端通过 | 对当前正式前端列明适用检查并实际执行；缺适用检查标待验，不能靠空配置通过 |
| 自检成功后 `通过` 不重新验证当前产物 | 接近推进时重新核查代码/配置与必需文件；发生相关变化先重验，不复用失效结果 |
| 阶段5在任务表中是收尾，但 verify 仍可能要求代码阶段检查 | 实际运行并报告缺口；不能把其他阶段的旧冒烟复制为本阶段真实调用，不能为收尾删验证条件 |

这些是 Skill 执行要求，不是独立防篡改保证。不能声称仓库脚本已修复或仅凭退出码证明产品可用。修复仓库脚本是另一个明确的实现任务，不在接入时静默改写。

检查状态用通过/失败/待验/不适用（附理由）；保留脚本原始输出，补充结论写在是否表说明与 S10/S11 报告中。测试缺失、无 Key、证据过期都不是通过。自检或补充核查失败时留在当前阶段，先修复再验。

功能和AI结果可跨站复用，但必须是同一相关实现、配置和标准且覆盖充分。只做了冒烟不得冒充正式评测；模型/Prompt/工具/数据链路变化重跑相关评测；部署环境变化补线上验证。

## 7. 交接与飞书

S10交给S11：接入记录、当前仓库阶段、技术基线、实现范围、代码版本、功能证据、AI跑分、未完成项和已验收记录。S11交给S12：准入范围、候选版本、限制、上线待验项和发布目标；测试通过不自动授权发布。

飞书模式沿用现有四表，不另建互不关联的题库/Bad case。原始日志、代码和运行产物不强制上传飞书；主文档/多维表记录版本、摘要及可访问证据链接，分享前检查脱敏和读者可访问性。分别报告工程验证与文档同步状态；同步未回读不标飞书交付完成，但不篡改已有工程事实。
