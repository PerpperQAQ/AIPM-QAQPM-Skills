# 产品体验流程（亲手跑一遍）

> 目标：拿到能支撑用户层与技术层判断的实际操作证据。体验结果用于旅程、效果评价与架构假设；只有需要量化比较时才评分。公开材料可补充分析，但与亲测、用户实际操作记录分别标注。

## 1. 选择体验路径（按顺序尝试）

| 顺序 | 条件 | 做法 |
|---|---|---|
| ① | 是网页产品，且运行本 skill 的 Agent 有浏览器操作类工具 | Agent 自己打开网页亲手用，每一步截图 |
| ② | Agent 用不了（只有 App / 移动端、拦截自动化操作、没有浏览器工具） | 先搜公开的演示视频、图文测评、官方教程和帮助中心，从中截取关键帧 |
| ③ | ② 仍然缺证据 | 给用户一份**具体的截图清单**，请用户自己操作后补图（清单见 §5） |

用户已经提供了截图或录屏时，直接按编号分析，记录操作人、任务、日期和覆盖步骤；能看见哪些结果就确认哪些，不改称 Agent 亲测。公开演示只证明演示中展示的行为，不能补成自己的实测。

## 2. 安全和花费边界

- **登录、注册、手机或邮箱验证码、人机验证、实名认证、付款，一律交给用户本人操作。** Agent 不输入账号密码，不读取或保存凭证，不替用户付款。遇到这些步骤就停下来，请用户接管，完成后再继续。
- **只用免费额度。** 需要消耗付费积分、开会员或者购买时，先告诉用户预计会花多少、为什么值得花，得到同意后再继续。
- 不在产品里公开发布作品，不对外发送内容，不改账号设置，除非用户明确要求。
- 涉及个人隐私的素材（真人照片等），只用用户提供或明确同意使用的。

## 3. 测试脚本与覆盖要求

先定任务、输入、输出验收标准、版本／日期、账号档位与环境；横比尽量使用相同材料，条件不同就说明影响。完整拆解至少取得一次主流程从输入到交付或明确失败点的实际操作记录，以及一次相关异常记录；是否正常跑通单独说明。四类异常均登记已测／未测／不适用及原因。本次决定若依赖某个异常，则必须补证或保留该结论待确认。单功能仅覆盖该链路及相关异常，不强制全产品深拆。

下列三轮是推荐组织方式，可以合并覆盖；边界探测按需要选用，不把次数当完成证据。

| 轮次 | 怎么测 | 想看什么 |
|---|---|---|
| ① 模糊需求 | 一句话、信息不全，例如"帮我做个视频" | 会不会追问或推表单 → 需求澄清分支、确认点 |
| ② 具体需求 | 真实场景下的完整需求（风格、时长、对象都给全） | 正常主流程、过程透出、端到端质量 |
| ③ 相关异常 | 选与任务有关的操作：信息给不全、中途改主意、局部修改；失败与退费通过允许的低风险测试或已有失败记录核对，不为凑覆盖制造付费、交易或违规行为 | 异常处理、回退、状态变化及真实扣费；未测项保留 |
| ④ 边界探测（按需） | 合法且在授权范围内的能力边界、输入长度、不同任务类型 | 行为边界与路径变化；用于提出架构假设，不能单凭变化确认 Agent |

拿不准时，换一个任务再跑一次。

## 4. 每一步记录什么（对应正向五步）

| 五步 | 必记 | 反推什么 |
|---|---|---|
| 入口 | 从哪进、默认文案、有哪些模式和模板 | 定位、目标用户 |
| 输入 | 让你给什么（对话 / 表单 / @引用 / 上传）、有哪些默认值 | 输入契约 |
| 过程 | 页面文案、状态、选项、进度、推荐列表、角色名、等待时长 | 哪些行为已发生；提示词、工具、状态机制或检索方式只是候选解释 |
| 输出 | 实际产出、对照任务标准的质量与瑕疵；量化评价按需 | 本次样本是否可用，不从成品外观猜型号或长期能力上限 |
| 交付 | 是否能打开、下载、继续编辑或使用，还需改多少；实际积分变化 | 用户的实际花费与使用障碍；厂商成本需另有证据或假设 |

每张截图按顺序编号（#1、#2……），文件名或描述里注明它属于哪一轮、哪一步。

## 5. 截图清单（请用户补图时用，按需删减）

1. 首页或入口（含模式选择、模板）
2. 输入界面（输入框、表单、默认文案）
3. 提交前的扣费或额度提示
4. 生成过程中的状态和思考文案、进度或任务打勾
5. 所有选择卡片或选项框（风格、模型、确认）
6. 最终输出，以及导出或下载页
7. 模糊需求时它的追问
8. 中途修改或局部修改的入口和结果
9. 失败或报错页，以及失败后的积分变化
10. 价格页或会员页、积分规则、模型下拉框

## 7. 完成状态与结果使用

逐产品登记状态和实际覆盖，不能仅按文档是否填满判断：

| 状态 | 可以说明什么 | 仍需写明 |
|---|---|---|
| 已完成约定体验 | 本次主流程及要求的异常已有可追溯实际操作记录；完整模式满足本节最低覆盖 | 操作者、覆盖任务、未测的其他异常、样本和环境限制；不代表覆盖所有功能或长期稳定 |
| 部分体验／待补实测 | 已有部分实际操作，未达到约定任务或异常覆盖 | 已完成到哪一步，缺口、原因、影响与补证动作 |
| 二手材料分析／待补实测 | 已分析公开演示或文档，尚无本次任务的实际操作证据 | 来源日期、可支持的结论、待亲测任务；不能声称已亲自完整体验 |
| 等待补证 | 已提出截图清单或接管请求，材料尚未取得 | 所缺内容与下一步；发出请求本身不算体验完成 |

实际操作失败也可以是有效体验证据：要记录尝试到的步骤、失败现象和影响，不能因此编出成功交付。若正常结果始终未能取得，写“主流程尝试失败／交付未验证”；分析可以得出受限结论，但不能勾选正常主流程已跑通。

- **→ 用户层**：形成旅程、异常覆盖与效果判断；启用评分时，每分能指回证据，未测不填 0。
- **→ 技术层**：用候选解释形成分工与架构假设，保留其他可能和核实办法，不从 UI 直接确认内部工具或多 Agent。
- **→ 模型层**：模型选项和实际扣费进入清单；等待时长只记录性能观察，不能独立确定型号或成本。
- 没测到的项写进「待核实清单」。

## 8. 纪律

- 产品或 Agent 说「已完成 / 已生成 / 已退款」时，**回页面看结果是否真的存在**（文件能打开、积分确实变了），没看到就不标【事实】。
- 只记录看到的；猜测标【推断】或【待确认】。
- 自己 Agent 的操作也一样：说"已截图""已提交"之前，先确认截图文件存在、页面状态已经变化。
