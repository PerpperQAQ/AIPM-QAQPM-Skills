# QAQPM · 核心技术难题梳理

帮助产品负责人说清三个问题：能向谁承诺什么，什么情况下会兑现不了，以及什么证据足以作决定。可在立项前、设计中或已有实现后单独调用。

## 从承诺找问题

1. **选一条真实用户路径。** 从本轮对话、项目文档和已有回执取出目标用户、操作、可观察结果、首版边界，以及用户已经想到的难点。用户说“除了 X”时将 X 当作已知条件，只在解释相邻依赖时提它。材料少也可先按一个明确假设推演；只有答案会改变排序时才追问。
2. **沿正常动作找失败分支。** 选取会让用户误以为“已经成功”的节点。追问哪个组件掌握事实，哪个组件真正能阻止错误，以及两个组件意见不一致时谁说了算。按业务选反例，例如旧请求晚到、权限刚收回、原始资料缺页、模型自信地漏掉重要项、供应商回执丢失。必要时检查质量、延迟和成本是否使首版承诺失去可行性。把反例翻译成用户会看到的结果。
3. **只保留会改变决定的问题。** 对每个候选补完一句：“如果这个假设不成立，我们必须改变＿＿，用户将只能＿＿。”填不出具体变化的先放到普通工程待办。优先讲错判后果重、证据薄弱、卡住下游或后期改造昂贵的项，并解释排序。通常深入前三项；有依据的不足三项就少列。已解决的问题只说明已覆盖的边界。
4. **让一次验证能选出一条路。** 针对每个优先项，用白话解释机制，指出用户或团队现在要做的取舍。提出一个有区分力的最小实验：给定什么输入或故障、观察哪个事实、怎样算通过、出现什么反例就应缩范围或换方案。分开写“产品现在可以怎么说”和“验证通过后才可以怎么说”。涉及业务容忍度或成本阈值而没有基线时，指出应由谁确认。实验默认是设计，实际执行按本轮授权范围处理。

## 交付给产品负责人

- 开头给出最该先懂的问题及其影响。每项把「失败场景 → 技术原因与负责组件 → 现有证据与缺口 → 产品取舍 → 最小验证」连成一段；多项需要比较时可用表格。用实际文档、代码位置或运行回执支持关键结论。按 QAQPM 的【事实】【推断】【待确认】标明性质，指出设计、底座能力、本机实测和真实用户验证分别证明哪一段。
- 收尾给一道来自该产品的情境题，尽量串起最高优先级的两项。附上回答时应能指出的事实、权限或成功判据，方便用户自测。若用户想现场练习，先出题，等其作答再对照。
- 默认在聊天中交付。已有 QAQPM 项目可附一句接手建议：范围取舍交 S5，立项前提交条件交 S6，判断效果的标准交 S7，准备做对照实验交 S9。专项本身不改变站序。用户要求沉淀经验时，再按「原提问、答案怎样影响判断、下次怎么问」追加到其指定文档。

## 颗粒度示例

用户承诺“同事可以随时接手正在开发的任务”。如果 A 断网但后台仍在改文件，只改负责人字段就让 B 开写，两人的改动可能互相覆盖。讨论应落到“首版承诺随时接手，还是仅在确认旧执行停止后接手”。最小验证是让 A 的命令保持在途，B 同时申请接手，检查实际文件写入与两方的执行回执。只有旧写入停止、旧请求失效后才让 B 动手，才能支持后一种承诺。换一个产品，重新从它的用户行为选反例。
