# QAQPM · MVP方案与范围（S5）

沿用 `05-MVP范围.md` 文件名。课堂MVP是较大的构建阶段；本站负责范围、方案首稿与验证安排，后续站完善同一份文档。

## 1. 入口与依赖

**用**：从需求池确定首版价值闭环、调整重大范围、启动AI能力方案。已有PRD只改细节转S8；痛点未证实转S2；用户只补一份专题文档可直接路由相应专题，不强制重跑全站。

读取S1问题、S2证据、S3需求、S4差异化、已有设计及已确认决策。涉及AI时读 [_shared/ai-document-protocol.md](_shared/ai-document-protocol.md)。

## 2. 推进顺序

1. 业务目标→目标用户→主任务链路→需求→优先级→资源，确定本轮是PoC、原型还是MVP。
2. 用Kano／价值成本确定必须、不做和以后；每条must回指痛点或已有需求ID，不把全部需求列P0。
3. 画出用户从输入到结果的核心链路，说明AI和人工分别负责什么；结合数据、成本、权限与交付条件完成架构取舍。
4. 按实际能力维护 [AI能力与文档清单](templates/AI能力与文档清单.md)，调用下表专题写MVP首稿；无AI时说明不适用，不建空包。
5. 用 [关键假设与验证计划](templates/关键假设与验证计划.md) 区分已决／待证。风险影响范围或投入时，可先调用S7最小评测设计，再由S9在已授权环境和预算中验证；证据回写S5/S6。尚无执行条件就交付计划与阻塞。
6. 确定通过／止损、分阶段检查与下一步。交S6立项或按任务返回S8；不因首稿齐全自动宣称技术已通过。

## 3. 专题路由与深度

| 条件 | 调用 | S5必须说清 |
|---|---|---|
| 产品Agent | `$qaqpm-agent-requirements` | 任务、职责、输入输出、主要流程、候选工具、边界及关键假设 |
| 知识检索生成 | `$qaqpm-rag-requirements` | 知识是否可得、来源范围、在线／离线主链路、更新需求、实际组件候选 |
| 生成或编辑内容 | `$qaqpm-aigc-requirements` | 创作任务、素材输入、输出规格、生成编辑流程、实际模态与采用条件 |

组合能力共享背景和定义，用ID／路径引用。S5首稿不强制填定模型、Top-K或所有接口字段；未知项写影响、验证方法与责任。S8沿用原文件细化开发与验收。

## 4. 输出与模板

- [05-MVP范围.md](templates/05-MVP范围.md)：目标、假设、主链路、范围、资源／架构取舍、通过与止损。
- [AI能力与文档清单.md](templates/AI能力与文档清单.md)：适用能力、组件、专题文件和评测对象；可合入05，小项目不强制独立文件。
- [关键假设与验证计划.md](templates/关键假设与验证计划.md)：已知依据、待证、验证方法、判定、结果与回流。
- 适用专题的需求首稿，推荐放`ai/`；已有路径优先。

来源：原S5范围方法＋CLASS-27与AG/RG/GC实例，见 [_shared/document-template-sources.md](_shared/document-template-sources.md)。

## 5. 架构取舍与通过线

保留执行位置、访问入口、租户与权限、工作区／数据归属、并发任务等适用取舍。选择必须有依据或标待确认；非Agent产品不硬填并发Agent数。S6/S9引用同一表。

- must与痛点相连，有不做理由；目标用户能走完一条价值链路。
- AI能力、专题首稿、模型／组件候选、未采用项与理由清楚。
- 首稿核心任务、输入输出与主链路不是空标题；暂未确定的技术细节有验证安排。
- 通过标准说明对象、分母、时间窗与采集方式；示例阈值不直接照搬。
- 文档、选择、运行和验收状态分别记录，正式冻结仍由后续阶段完成。

## 6. 交接与回流

人话先写接手后第一步，再附既有YAML。沿用`mvp_must`、`mvp_wont`、`pass_fail_criteria`；按需增`ai_document_index_path`、`capability_ids`、`document_maturity: mvp_draft`、`validation_plan_path`。路径必须存在或标待创建。下一站通常S6；早期验证结束回S5/S6，不直接跳开发。

PoC失败缩范围或换方案；差异化被砍回S4；问题不成立回S1/S2。HTML按交付需要生成。
