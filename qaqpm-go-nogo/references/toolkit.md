# 方法工具箱（拆到细处时查）

## 1. 借 AI 取证的 prompt（把截图或材料交给另一个 AI 时用）

```
你是 AI 产品拆解助手。我按顺序上传了「产品名」从提出需求到拿到结果的截图，已按 1、2、3……编号，还附上了官网、价格页、帮助中心的截图或原文。
只根据我给的材料回答，不要用宣传文案或你自己的常识补充。
按下面五个问题逐一回答，每个问题写成几条短结论：
一、用户为什么用它：写成一句话「一款给【谁】用的、在【什么场景】下、解决【什么问题】的【什么产品】」；如果是 B 端，分别写用的人、买单的人、验收的人
二、怎么用它把这件事做完：按入口、输入、过程、输出、交付五步写；再写信息给不全、失败、中途改主意、不满意这四种情况它各怎么处理
三、哪一步 AI 做、哪一步人做、怎么做：列出每一步是 AI 做还是人做；人做的地方为什么要人；它更像 Chatbot、Workflow、Agent 还是多 Agent，依据是什么
四、每一步用什么模型、花多少钱：列出看得到的模型和档位；怎么收费，做一次大概扣多少
五、什么是别人买不到的：先列买得到的（模型、算力、通用工具），再列剩下的，说说壁垒可能在哪
每条结论都标一类：
【事实】材料里直接看得到，注明截图编号或原文
【推断】由几条事实推出，写出依据
【待确认】材料不够
```

## 2. 判断"下一步谁决定"（Agent 光谱）

| 形态 | 下一步由谁定 | 典型信号 | 什么时候该用 |
|---|---|---|---|
| Chatbot | 用户 | 问一句答一句 | 纯问答，靠模型 + 系统提示词就够 |
| Workflow | 人提前摆好 | 步骤固定，每次一样；单次生成 | 流程和输出都固定、能穷举、便宜又稳定 |
| Agent | 模型 | 有计划、进度和子任务；步骤随任务变 | 不能穷举的开放任务 |
| 多 Agent | 多个模型分工 | 多个角色或岗位；子任务并行或串行交接 | 原来就是一群人干的活；单 Agent 上下文会爆 |

链式、路由、并行只是 Agent 之间的连法。

**从外部判断的方法**：
1. 看页面信号：有没有计划、进度、子任务，在哪停下来问你，有没有任务回放。
2. 换个任务再跑一次：步骤跟着任务变 → Agent；步骤不变 → Workflow。
3. 测边界：能力范围内外的场景都跑，看它会不会事先说明，过程透出多少。
4. 自己搭一个复现：搭不出同样效果，就说明背后还有别的能力。
5. 去 GitHub 搜同类开源实现。

**多 Agent 的代价**：更贵（多次调用模型）；错误会连乘（每步 90%，串五步约 59%），所以关键节点要让人确认方向。串行通常是因为业务本身就是串行的（剧本确认了，后面才能做）。

## 3. 确认点四种放法

| 放法 | 例子 | 适用 |
|---|---|---|
| 动手前审方案 | 计划模式："你确认了才开干" | 长任务、贵任务 |
| 风险动作前停下来 | 登录交给用户；付款、对外发送、真人出镜校验前停下 | 不可逆、要担责的动作 |
| 事先给额度 | 商家设好赔付上限，额度内 AI 自己办 | 高频小额决策 |
| 用户自己调档 | 始终询问 / 按需确认 / 全部允许 | 用户熟练度差异大 |

展示方式：选项卡片、多方案选一、提交前显示扣费，通常都好过开放式提问。和钱有关的地方都要确认；因为平台原因出错，要考虑退积分。

## 4. 单个 Agent 四步推导

**① 逻辑梳理**：输入 → 处理（判断分支：需求明确 / 不明确要追问 / 涉及风险比如 IP 或真人）→ 输出。每个分支写出调了哪个工具、在哪推卡片让人确认。

**② 构成推导**

| | ReAct | Planner-Executor |
|---|---|---|
| 适合 | 探索型、对话式的开放任务，要不断获取外部信息、修正下一步 | 生产型的长链路、高耦合任务 |
| 优点 | 灵活 | 通过字段更新做强状态管理；天然支持审批流和人工介入；能断点续传，出错只回滚那一步 |
| 缺点 | 出错时产生大量中间 token；依赖上下文窗口，容易忘事 | 灵活性低，需要提前设计好流程 |

**③ 工具推导**（从 UI 和过程文案反推）

| 工具类型 | 例子 | 怎么看出来 |
|---|---|---|
| 生成类 | 提示词编译、生图、生视频、TTS、合成 | 过程里写着"调用 xx 生图中" |
| 检索类 | RAG 风格库或知识库检索 | 从大库里推荐前 N 个 |
| 交互类 | 表单卡片、选择卡片、追问 | 固定格式的选项、固定数量的候选 |
| 上下文和状态类 | 读写全局字段、状态回滚 | 交接时有摘要；任务打勾；能回退 |
| 调度类 | 把任务派给下游 Agent | "邀请 xx 进群" / 切换角色 |
| 计价类 | 按数量估算报价 | 出报价单 |
| 代码步骤（不需要 AI） | 按顺序拼接、裁剪 | 结果确定、没有创意成分 |

为什么要封装成 tool：输入输出非常确定（比如"正好 5 个情绪词"），可以复用，还能避免模型夹带多余的话。

**④ 提示词推导**（固定七段；硬约束和输出契约最见功力）

```
## 1. 角色定义 Role：你是谁，在流程里排第几站，上下游是谁，遵守什么模式（如 Plan-and-Execute）
## 2. 输入契约 Input Contract：从哪触发；每次激活先读哪些上下文字段
## 3. 输出契约 Output Contract：只写哪些字段；严禁写哪些字段（防止越权）
## 4. 硬约束 Hard Constraints：不准跨步；候选只能来自工具返回；确认后才写入；修改必须回滚；只输出 JSON
## 5. 任务流程 Workflow：Step A…F（含分支、局部重写、任意时刻都能回滚）
## 6. 工具规范 Tool Instructions：每个工具的签名、入参、返回和使用原则
## 7. 输出格式 Response Format：严格 JSON，例如 {tool_calls, form_card, 产物, next_action, next_hints}
```

## 5. 全局上下文和状态管理（多 Agent 必拆）

- **全局上下文 = 整个项目的 PRD**。每个 Agent 只读自己需要的字段、只写自己负责的字段，字段之间强引用（用 ID 引用，不复制内容）。
- 字段骨架：项目元数据（id、版本、技术规格）· 核心内容字段（摘要、基调、风格标签、数量）· 实体字典（角色等，含 id 和资产 URI）· 资产流水线（逐镜头或逐步骤的描述、资产、时长、引用）· 确认日志 approval_log。
- **状态管理**：进行中 / 已完成 / 未完成。上一步没完成，下一步不能开始。用户修改时，判断改的是当前结果还是上游结果，再回滚到稳定节点、交回对应的 Agent（逆向流程）。提示词里的规则是软约束，代码里"通过了才能往下走"是硬约束。
- 违规和 IP 防护：识别节点放在最前面（主 Agent 初判时），命中后推卡片让人选择，或者走专用模型或策略。

## 6. 「它没做好的地方」分析框架

现象（截图）→ 可能原因（工具调用失败 / 状态没更新 / 提示词没约束 / 模型能力不足）→ 解决方案分三层：
- 提示词："确认后立即调用下一步工具，严禁重复口头确认"
- 工具：状态已经是 confirmed 时直接返回成功，做成幂等
- 编排：连续两次输出相同内容时，主 Agent 介入检查状态，启用备用方案

## 7. 模型层判断要点

- 先按 Agent 需要的能力定模态，再定型号和档位，最后看现成模型解决不了时要不要微调或训练。
- 数据不能外流就本地部署开源模型（一次性硬件投入，换掉按量付费的 API）；有些公司因为合规不能用国外模型。
- 能不能换：换模型必须先做选型和评测（参数不兼容、规则太多反而压制强模型、延迟）。
- 档位跟着需求走：要电影质感，还是发出去能有点赞就行？
- 固定能力（抠图、换背景、裁剪）用传统小模型更便宜。
- 场景决定模型：实时性和真人还原度要求高时，可能用端到端的单一模型，而不是多模型组合。
- 每个模型都要能回答："这个场景为什么选这个模型？"

**成本口径**：钱花在哪（每次调模型、强模型更贵、机器或沙箱、第三方接口）→ 怎么收回来（按次、按通、按积分、分档订阅、广告）。Token 是变动成本，用户越多花得越多。Agent 执行一次任务的成本可能是 Chatbot 的上百倍，所以缓存命中率、默认档位、免费额度设计都直接决定生死。

## 8. 基础层判断要点

- 怎么查：先划掉模型和算力 → 看隐私政策里数据怎么用 → 看接了哪些自家系统 → 看官方访谈。
- 最值钱的是**越用越多**的那种：用户资产（可复用）、会话（"生成得一点都不好"就是 badcase）、风格库或知识库、skill。
- 闭环例子：用户选的是 3D 风格，结果生成了真人感 → 先查流程，流程没问题就去优化风格库对应的 skill → 收进评测集回归测试。
- 代码通常不是壁垒（同类开源很多）；壁垒是用户数据、标准化工作流、封装好的提示词和 skill，以及业务接口和权限（"平台外的软件只能说，不能办"）。

## 9. 汇总用的两张清单

- **PM 在 AI 产品里的三件事**：体验设计（每一步的交互和默认文案）· 能力边界（不做什么、优先级）· 信任设计（透出过程、确认点、失败退款）。
- **Demo 到完整产品的五个差距**：给谁用 · 出了错怎么办 · 稳不稳（抽卡率从 1/10 提到 9/10，再到 99/100）· 账算不算得过来 · 凭什么选你。

## 10. 背景：传统产品 vs AI 产品

| 问题 | 传统产品 | AI 产品 |
|---|---|---|
| 为什么用 | 给谁用、解决什么问题 | 一样，定位永远不变 |
| 怎么用 | 每一步自己点 | 下目标 → 在确认点拍板 → 验收 |
| 谁来做 | 人做，软件按写死的规则执行 | AI 做，人在关键处拍板 |
| 用什么、花多少钱 | 代码，每次一样，边际成本接近 0 | 模型，每次不一样、会出错，每次都花钱 |
| 什么买不到 | 做出来的功能、攒下的用户 | 模型谁都能买，壁垒在数据和场景 |
